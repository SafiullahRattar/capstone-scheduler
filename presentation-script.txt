PRESENTATION SCRIPT: Academic Audit Parsing
Safiullah Rattar | SYSC 4907 - Carleton Smart Course Scheduler
Duration: 10-15 minutes


[SLIDE 1: TITLE SLIDE]

"Good morning everyone. Today I'm presenting Academic Audit Parsing, which is a component of the Carleton Smart Course Scheduler. I'll be walking you through how we extract student course data from PDF audits and some performance optimizations we implemented."


[SLIDE 2: THE PROBLEM]

"Let me start with the problem we're solving. Carleton University provides student academic data exclusively as a downloadable PDF audit from Carleton Central. There's no API available.

On the left, you can see what we receive: a PDF file containing the student's entire academic history with unstructured text. The challenge is transforming this into the structured JSON data shown on the right - separating completed courses, current courses, grades, and student information. This structured data is essential for our scheduler to function."


[SLIDE 3: WHY NOT OCR?]

"You might wonder: why not just use OCR? Optical Character Recognition like Tesseract or vision APIs works by rendering the PDF as an image and recognizing characters.

The problem is that OCR is probabilistic - it makes errors. For example, it might confuse the letter 'B' with the number '8', or 'I' with '1'. When you're dealing with grades, these errors are critical. Misreading an 'F' as something else could mark a failed course as passed, which would break prerequisite validation.

Instead, we use PDF text stream extraction with the `pdftotext` tool. This extracts the actual character encoding directly from the PDF binary, which is deterministic and much faster. The main challenge is that the extracted text lacks structure, so we have to reconstruct the layout."


[SLIDE 4: THE LAYOUT PROBLEM]

"Let me show you the layout challenge. By default, `pdftotext` extracts text in column-major order - it reads the first column completely, then moves to the second. As you can see, this breaks the association between terms and courses. Term '22FA' appears on line 2, but the corresponding course 'COMP 2804' is on line 7.

Using the `-layout` flag solves this. It uses character coordinates within the PDF to reconstruct the visual layout, giving us row-major output where each line contains all the fields for one course entry."


[SLIDE 5: PROCESSING PIPELINE]

"Our processing pipeline has three main steps. First, the user uploads a PDF which we write to a temporary file. Second, we use `pdftotext -layout` to extract the text while preserving the visual structure. Third, we parse that extracted text using regex patterns to extract the structured data. Finally, we clean up the temporary files.

This entire process happens on the server side in a single request, making it fast and stateless - the user doesn't need an account, they just upload their audit and get immediate results."


[SLIDE 6: COURSE EXTRACTION PATTERN]

"The core of our parsing is this regex pattern. Let me break down what each capture group does.

The first group captures the term: two digits for the year, followed by FA, WN, or SU for the semester. Next we capture the department code, like SYSC or COMP. Then the four-digit course number. Then the credit value as a decimal. Finally, the grade with modifiers like A-plus or B-minus. The last optional capture group handles status flags like CUR for current, RP for repeated, and so on.

This pattern matches exactly how Carleton formats course entries in the audit, allowing us to extract all relevant fields in one pass through the document."


[SLIDE 7: PROCESSING MATCHES]

"To process the text, we use JavaScript's `matchAll` method with global and multiline flags. This finds all matches throughout the document and gives us access to each captured group.

For each match, we extract the individual fields. Note that we normalize the course ID by removing the space - so 'SYSC 3303' becomes 'SYSC3303'. This is important because our database stores course IDs without spaces, so normalization ensures we can look up course information later.

The `matchAll` approach is efficient because it processes the entire audit in a single pass, giving us all courses with their associated data."


[SLIDE 8: GRADE CLASSIFICATION]

"Once we have the course data, we need to classify it correctly. We check if a course is marked as 'CUR' or has a status indicating it's currently in progress.

Current and deferred courses go into the `currentCourses` array with their term information. Completed courses with passing grades go into `completedCourses` with their grade. We filter out failures - F, X, UNS, and NR grades don't satisfy prerequisites.

The key insight is that both current and completed courses can satisfy prerequisite requirements for taking future courses, but they're treated differently when grade requirements come into play, which I'll explain next."


[SLIDE 9: WHY SEPARATE CURRENT VS COMPLETED?]

"Why separate these two categories? Both current and completed courses can satisfy the basic prerequisite requirement that you've 'taken' a course. For example, if you're currently taking SYSC 3303 and want to take SYSC 4406 next term which requires it, that prerequisite is satisfied.

However, some prerequisites have minimum grade requirements, like 'C- or higher'. Completed courses have grades, so we can verify the requirement is met. Current courses don't have grades yet, so we can't verify grade requirements. In this case, current courses satisfy the 'course taken' condition but not the grade condition.

This separation allows our scheduler to give accurate feedback about which requirements are satisfied and which are still pending."


[SLIDE 10: HANDLING REPEATED COURSES]

"Students sometimes retake courses, so we need to handle duplicates. We use two sets to track what we've seen - one for completed courses and one for current courses.

Since the PDF is organized chronologically with older terms first, when we encounter a repeated course, we check if it's already in our completed courses list. If it is, we overwrite the older grade with the newer one. This is important because students often retake courses to improve their grades.

For example, if the audit shows SYSC 2004 with a C-minus in the Fall term and a B-plus in the Winter term, we initially add the C-minus. When we encounter the B-plus, we overwrite the C-minus with the B-plus. This ensures our system correctly identifies that the student meets prerequisites requiring B-plus or higher, reflecting their actual academic standing."


[SLIDE 11: STUDENT INFO EXTRACTION]

"Beyond courses, we also extract student information using simpler regex patterns. The student ID is the first nine-digit number in the document. The name is extracted in 'Lastname, Firstname' format and reordered to 'Firstname Lastname'. And the program is extracted from text following 'Bachelor of Engineering'.

These patterns are more forgiving than the course pattern because student info appears less consistently in audits. But they're sufficient for our purposes - we need the student ID and program for validation, and the name is displayed in the UI for confirmation."


[SLIDE 12: HOW PARSED DATA IS USED]

"So how is all this parsed data used? There are two main applications.

First, prerequisite validation. When a user selects a course to add to their schedule, we check whether the required courses are in their completed or current course lists, and whether any grade requirements are met. This happens in real-time as users build their schedule.

Second, schedule generation. Users upload their audit, select courses they're interested in, and our system uses the parsed data to filter out courses they've already completed, validate prerequisites for their selections, and generate conflict-free schedules. All of this happens in one session without requiring user accounts."


[SLIDE 13: AUDIT PARSING SUMMARY]

"To summarize the audit parsing section: our technical approach uses `pdftotext -layout` for deterministic text extraction, regex patterns for fast parsing, and careful grade classification to handle various academic statuses.

Our key design decisions: choosing `pdftotext` over OCR for accuracy, using the `-layout` flag to preserve row structure, using regex for its simplicity and speed, separating current from completed courses for proper grade validation, using sets to handle course repeats, and filtering out failed grades since they don't satisfy prerequisites.


[SLIDE 14: COURSE SEARCH: THE PROBLEM]

"Now let's move to the second part of my presentation: search optimization. When users search for courses, they type in a search box and expect real-time results.

The problem is that a naive implementation makes an API call and database query for every keystroke. If a user types 'SYSC4001', that's eight keystrokes, meaning eight separate database queries. This creates unnecessary server load, especially with concurrent users, and provides a poor user experience as results flicker with each response."


[SLIDE 15: THREE OPTIMIZATION STRATEGIES]

"We implemented three strategies to solve this. First, a minimum length threshold - we don't search for queries under two characters. Single letters match too many courses and aren't useful anyway.

Second, debouncing - we wait 300 milliseconds after the user stops typing before making an API call. This means we only execute one search for a rapidly typed query, not one per keystroke.

Third, caching - we store search results in memory for five minutes. If a user searches for the same course again, or another user searches the same term during a session, we return cached results without hitting the database.


[SLIDE 16: DEBOUNCING IMPLEMENTATION]

"Here's how debouncing works. We use a reference to store a timer ID. Each time the user types, we clear any existing timer and start a new one. The search only executes after the timer expires, meaning the user has stopped typing for 300 milliseconds.

This is implemented with a `useRef` to persist the timer across renders. The effect is that typing 'SYSC4001' quickly results in exactly one API call, not eight. The user sees stable results and the server receives one well-formed query instead of multiple partial ones."


[SLIDE 17: CACHING IMPLEMENTMENT]

"For caching, we use an in-memory Map that stores query results with timestamps. When a search is requested, we first check if we have a cached result for that query. If the cache is less than five minutes old, we return it immediately without any API call. Only on a cache miss do we fetch from the database and store the result.

The cache lives in browser memory, not localStorage, so it's cleared when the tab closes. A five-minute TTL covers typical usage patterns without risking stale data - course data doesn't change during a user session, and five minutes is long enough to benefit from repeated searches but short enough that data doesn't become outdated."


[SLIDE 18: BACKEND SEARCH ENDPOINT]

"On the backend, our search endpoint is straightforward but efficient. It accepts a query and an optional limit parameter. We search both course IDs and titles case-insensitively, so users can search by code like 'SYSC3303' or by title keywords.

We filter to only show courses that have available sections - there's no point showing a course that can't be scheduled. Results are limited to 20 by default with a maximum of 100 to prevent overwhelming the UI or the database.


[SLIDE 19: OPTIMIZATION RESULTS]

"These optimizations have a significant impact. Let's look at some scenarios. Typing 'SYSC4001' went from 8 requests down to 1. Searching for 'SYSC' twice went from 2 requests to 1 thanks to caching. Typing a single character 'S' and deleting it went from 1 request to 0 because of the minimum length threshold. And a complex typing pattern with pauses went from many requests down to just 2.

In a typical session with 50 or more keystrokes, we only need about 5 to 10 actual searches. Combined, these strategies dramatically reduce API calls and server load while improving user experience.

To summarize: minimum length filtering eliminates useless queries, debouncing consolidates typing into single searches, and caching avoids repeated queries for the same terms.


[CONCLUSION]

 "In conclusion, our PDF parsing approach provides accurate, deterministic extraction of student course data using text stream extraction and regex patterns. Our search optimizations significantly reduce server load while improving user experience through debouncing and caching. Together, these components enable the Carleton Smart Course Scheduler to function efficiently without requiring user accounts or persistent sessions.

 Thank you for your attention. I'm happy to answer any questions."

[DATA STRUCTURE DETAILS]

StudentAuditData Interface:
- studentId: string - 9-digit student number, extracted as first 9-digit sequence in PDF
- name: string - Full name, reordered from "Last, First" to "First Last"
- program: string - Program name extracted from "Bachelor of Engineering - [Program]" pattern
- completedCourses: Array<{courseId, grade}> - Successfully completed courses with grades
- currentCourses: Array<{courseId, term}> - Currently enrolled courses with term identifier
- requirements: RequirementInfo[] - Degree requirements from the audit

RequirementInfo Interface:
- title: string - Name of requirement (e.g., "SYSC 4907" or "4.0 credits in...")
- status: 'OK'|'NO'|'IP'|'NONE' - OK=satisfied, NO=missing credits, IP=in progress, NONE=not applicable
- creditsRequired: number - Total credits needed for this requirement
- creditsCompleted: number - Credits already earned toward this requirement
- creditsInProgress: number - Credits currently enrolled that count toward this requirement
- courseOptions: string[] - Array of course codes that satisfy this requirement

[WHY REQUIREMENTS ARRAY STORES courseOptions]

The requirements array stores which courses can fulfill each degree requirement. For example:
- Requirement: "4.0 credits in NET 4001, NET 4005, NET 4007"
- courseOptions: ["NET4001", "NET4005", "NET4007"]

The scheduler uses this to:
1. Check which requirements are satisfied by comparing against completedCourses and currentCourses
2. Calculate remaining credits: creditsRequired - creditsCompleted - creditsInProgress
3. Suggest courses to take next by looking at courseOptions from unfulfilled requirements
4. Filter out already-taken courses from suggestions

[ALGORITHM: PARSE AUDIT PDF - LINE BY LINE]

1. Extract student info (lines 282-289):
   - Student ID: First 9-digit number found with regex /(\d{9})/
   - Name: Pattern "Lastname, Firstname" → reordered to "Firstname Lastname"
   - Program: Text after "Bachelor of Engineering - "

2. Initialize data structures (lines 292-295):
   - completedCourses: [] - array to store finished courses
   - currentCourses: [] - array to store in-progress courses
   - seenCompleted: Set<string>() - tracks courses already added to completed
   - seenCurrent: Set<string>() - tracks courses already added to current
   - Sets used for O(1) lookup instead of O(n) array search

3. Define course line regex (line 298):
   - ^\s*(\d{2}(?:FA|WN|SU))\s+([A-Z]{3,4})\s+(\d{4})\s+([\d.]+)\s+([A-Z+\-]+)(?:\s+(?:RP|CUR|SAT|TR|UNS|IP|DEF))?/gm
   - ^ matches line start
   - \s* allows leading whitespace
   - (\d{2}(?:FA|WN|SU)) captures term (22FA, 23WN, 24SU)
   - \s+ whitespace separator
   - ([A-Z]{3,4}) captures department (SYSC, COMP, ELEC, MATH)
   - \s+ whitespace separator
   - (\d{4}) captures course number (3303, 4907)
   - \s+ whitespace separator
   - ([\d.]+) captures credits (0.50, 0.25, 1.00)
   - \s+ whitespace separator
   - ([A-Z+\-]+) captures grade (A+, A, A-, B+, etc.)
   - (?:\s+(?:RP|CUR|SAT|TR|UNS|IP|DEF))? optional status flags
   - /gm flags: global (all matches) and multiline (^ matches each line)

4. Extract all matches (line 300):
   - matchAll returns iterator, convert to array
   - Processes entire document in one pass - O(n) where n = document length

5. Process each match (lines 302-321):
   - Extract term, courseCode, courseNum from capture groups
   - Concatenate: courseCode + courseNum = "SYSC" + "4907" = "SYSC4907"
   - This normalization matches database format (no spaces)
   - Check if current: fullMatch includes 'CUR' or 'DEF', or grade equals 'CUR' or 'DEF'
   - If current and not seenCurrent:
     - Add to currentCourses array with term
     - Add to seenCurrent set to prevent duplicates
   - If completed (has grade, not CUR/DEF/UNS/F/X/NR) and not seenCompleted:
     - Add to completedCourses array with grade
     - Add to seenCompleted set to prevent duplicates

6. Extract requirements (line 323):
   - Calls extractRequirementsFromPDF()
   - This function looks for patterns like "4.0 credits in NET 4001, NET 4005"
   - Extracts course list and determines status (OK/NO/IP)
   - Returns array of RequirementInfo objects

7. Return assembled data structure (lines 325-332)

[DECISION: WHY TWO SETS FOR DEDUPLICATION]

We use separate sets (seenCompleted and seenCurrent) because:
1. Same course can appear as completed AND current (student retaking)
2. Sets provide O(1) lookup vs O(n) for array.includes()
3. Prevents adding same course twice to same array
4. Example: SYSC2004 failed in 21FA, retaking in 22FA
   - First match: grade='F' → not completed, not current (F filtered out)
   - Second match: grade='CUR' → currentCourses, seenCurrent.add('SYSC2004')
   - If student takes again and completes, new entry goes to completedCourses

[ALGORITHM: HANDLING REPEATED COMPLETED COURSES]

Key insight: PDF is chronological (oldest term first)
Therefore, later matches = more recent grades = better grades

Logic (lines 312-321):
1. When encountering a completed course (not CUR/DEF/UNS/F/X/NR):
2. Check if courseId already exists in completedCourses array
3. If exists (findIndex >= 0):
   - Overwrite the grade with newer one
   - Example: C- → B+ (student improved grade)
4. If new:
   - Add to completedCourses
   - Add to seenCompleted set

Why this works:
- F grades: filtered out by grade check
- C- then B+: C- added first, then B+ overwrites
- B+ then A+: B+ added first, then A+ overwrites
- Prerequisite validation sees best grade
- Correctly handles "B+ or higher" requirements

Example scenario:
```
21FA  SYSC 2004  0.50  C-    → Added: {courseId: "SYSC2004", grade: "C-"}
22FA  SYSC 2004  0.50  B+    → Overwrites: {courseId: "SYSC2004", grade: "B+"}
```

Prerequisite check: "SYSC2004 with B+ or higher"
- System sees: B+
- Result: ✅ Satisfied (not with old C-)

Time complexity: O(n * c) where n = matches, c = current completed courses
Space complexity: O(c) for completedCourses array

[DECISION: WHY FILTER OUT FAILING GRADES]

Filtered grades: F, X, UNS, NR, DEF (treated as current), CUR (treated as current)
Reason: Failed courses don't satisfy prerequisites
Example: Student fails SYSC2004 with F grade
- We don't add to completedCourses
- Scheduler correctly identifies SYSC2004 as unfulfilled prerequisite
- When student retakes and gets B+, that grade is recorded

[DECISION: NORMALIZE COURSE IDs]

PDF has: "SYSC 3303" (with space)
Database stores: "SYSC3303" (no space)
We remove space during parsing to match database format
Allows efficient lookups: database query WHERE id = 'SYSC3303'

[DECISION: WHY MATCHAll INSTEAD OF SPLIT/LOOP]

Alternative: Split text by lines, parse each line with regex
matchAll approach:
- Single pass through document - O(n)
- Built-in iterator is efficient
- Returns all matches with captured groups directly
split/loop approach:
- Splitting creates array of all lines - O(n) memory
- Must iterate and apply regex to each line - also O(n) but more code
- matchAll is cleaner and more idiomatic JavaScript

[ALGORITHM: GET REMAINING COURSES]

function getRemainingCourses(auditData):
1. Create Sets from completed and current courses for O(1) lookup
2. Initialize empty Set for remaining courses
3. For each requirement in auditData.requirements:
   - Calculate credits needed: required - completed - inProgress
   - If credits needed > 0:
     - Get courseOptions (courses satisfying this requirement)
     - For each course option:
       - If not in completed AND not in current:
         - Add to remaining courses Set
4. Convert Set to array and sort alphabetically

Time complexity: O(r * c) where r = requirements, c = courses per requirement
Space complexity: O(u) where u = unique remaining courses

[DECISION: WHY SET FOR REMAINING COURSES]

Using Set prevents duplicates:
- Two different requirements might include the same course as option
- Example: SYSC4001 might satisfy both "technical elective" and "SYSC elective"
- Set automatically handles deduplication
- Final conversion to array produces unique, sorted list

[ALGORITHM: SEARCH OPTIMIZATION COMBINED]

Combined effect of three strategies:

Without optimization:
User types "SYSC4001" (8 chars) → 8 API calls, 8 DB queries

With minimum length (2 chars):
"S", "SY" blocked → 6 API calls, 6 DB queries

With debouncing (300ms):
All 8 chars typed within 300ms → 1 API call, 1 DB query

With caching (5min TTL):
Search "SYSC" → API call, DB query, cache result
Search "SYSC" again → cache hit, no API/DB

Best case: Typing "SYSC4001" fast, then searching "SYSC" again
→ 1 API call total

[DECISION: WHY 300ms DEBOUNCE]

300ms balances responsiveness and efficiency:
- Too short (100ms): Still many partial queries
- Too long (1000ms): User perceives lag
- Human typing average: 200-300ms between keystrokes
- 300ms catches most typing without feeling sluggish

[DECISION: WHY IN-MEMORY CACHE NOT LOCALSTORAGE]

In-memory Map (browser tab):
- Pros: Fast (no serialization), automatic cleanup on tab close, no quota limits
- Cons: Lost if tab refreshed, not shared across tabs
- localStorage:
  - Pros: Persists across tabs, refreshes
  - Cons: Slower (JSON serialization), limited to ~5MB, must manually manage TTL

We chose in-memory because:
- Course data doesn't need to persist across sessions
- User re-uploads audit each visit anyway
- Performance matters more than persistence
- Avoids managing cache invalidation across sessions

[DECISION: WHY 5 MINUTE TTL]

Course data changes infrequently:
- Course catalog updates once per term
- Schedules update before term starts
- During session (typically <30 minutes): no changes expected
- 5 minutes long enough to benefit from caching
- 5 minutes short enough to minimize stale data risk

Alternative: No TTL (cache forever)
- Risk: User might see stale course availability
- Better to err on side of fresh data

[EDGE CASES HANDLED]

1. PDF parsing - malformed course lines:
   - Regex only matches well-formed lines
   - Badly formatted lines ignored gracefully
   - Doesn't crash on partial data

2. Missing student info:
   - studentIdMatch, nameMatch, programMatch checked for null
   - Empty strings used as fallback
   - System continues with partial data

3. Duplicate courses:
    - Sets prevent duplicates in same category
    - Retakes handled by overwriting with newer grade (PDF is chronological)
    - Example: C- (old) → B+ (new), keeps B+

4. Failed courses retaken:
    - F grade filtered out (doesn't satisfy prerequisites)
    - Current CUR or later completion added
    - Retaken passing grade overwrites earlier attempts
    - User sees accurate academic standing

5. Elective categories:
   - "CS_ELECTIVE" expanded to actual course list
   - Allows requirement tracking for electives
   - Simplified mapping (hardcoded in development)

6. Prerequisite validation:
   - Both completed and current satisfy "course taken"
   - Only completed satisfy "grade requirement"
   - Accurate feedback for planning

[COMPLEXITY ANALYSIS]

PDF Parsing:
- Time: O(n) where n = PDF text length (single regex pass)
- Space: O(m) where m = number of courses (arrays + sets)

Remaining Courses Calculation:
- Time: O(r * c) where r = requirements, c = avg courses per requirement
- Space: O(u) where u = unique remaining courses

Search with optimizations:
- Without cache: O(1) per query after min length and debounce
- With cache hit: O(1) (no DB query)
- Cache space: O(k) where k = unique queries in 5 minutes

[ALTERNATIVE APPROACHES CONSIDERED]

1. OCR for PDF parsing:
   - Rejected due to probabilistic errors
   - Character confusion (B/8, I/1, 0/O)
   - Critical for grade accuracy

2. PDF parsing library (pdf.js):
   - More complex to implement
   - pdftotext is simpler, deterministic
   - Already proven reliable for text extraction

3. Database-level full-text search:
   - Would require PostgreSQL or specialized index
   - Current approach (LIKE with case-insensitive) is simpler
   - Sufficient for <1000 courses

4. Redis for caching:
   - Overkill for single-session use case
   - In-memory browser cache is adequate
   - Avoids additional infrastructure
