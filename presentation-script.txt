PRESENTATION SCRIPT: Academic Audit Parsing
Safiullah Rattar | SYSC 4907 - Carleton Smart Course Scheduler
Duration: 10-15 minutes


[SLIDE 1: TITLE SLIDE]

"Good morning everyone. Today I'm presenting Academic Audit Parsing, which is a component of the Carleton Smart Course Scheduler. I'll be walking you through how we extract student course data from PDF audits and some performance optimizations we implemented."


[SLIDE 2: THE PROBLEM]

"Let me start with the problem we're solving. Carleton University provides student academic data exclusively as a downloadable PDF audit from Carleton Central. There's no API available.

On the left, you can see what we receive: a PDF file containing the student's entire academic history with unstructured text. The challenge is transforming this into the structured JSON data shown on the right - separating completed courses, current courses, grades, and student information. This structured data is essential for our scheduler to function."


[SLIDE 3: WHY NOT OCR?]

"You might wonder: why not just use OCR? Optical Character Recognition like Tesseract or vision APIs works by rendering the PDF as an image and recognizing characters.

The problem is that OCR is probabilistic - it makes errors. For example, it might confuse the letter 'B' with the number '8', or 'I' with '1'. When you're dealing with grades, these errors are critical. Misreading an 'F' as something else could mark a failed course as passed, which would break prerequisite validation.

Instead, we use PDF text stream extraction with the `pdftotext` tool. This extracts the actual character encoding directly from the PDF binary, which is deterministic and much faster. The main challenge is that the extracted text lacks structure, so we have to reconstruct the layout."


[SLIDE 4: THE LAYOUT PROBLEM]

"Let me show you the layout challenge. By default, `pdftotext` extracts text in column-major order - it reads the first column completely, then moves to the second. As you can see, this breaks the association between terms and courses. Term '22FA' appears on line 2, but the corresponding course 'COMP 2804' is on line 7.

Using the `-layout` flag solves this. It uses character coordinates within the PDF to reconstruct the visual layout, giving us row-major output where each line contains all the fields for one course entry."


[SLIDE 5: PROCESSING PIPELINE]

"Our processing pipeline has three main steps. First, the user uploads a PDF which we write to a temporary file. Second, we use `pdftotext -layout` to extract the text while preserving the visual structure. Third, we parse that extracted text using regex patterns to extract the structured data. Finally, we clean up the temporary files.

This entire process happens on the server side in a single request, making it fast and stateless - the user doesn't need an account, they just upload their audit and get immediate results."


[SLIDE 6: COURSE EXTRACTION PATTERN]

"The core of our parsing is this regex pattern. Let me break down what each capture group does.

The first group captures the term: two digits for the year, followed by FA, WN, or SU for the semester. Next we capture the department code, like SYSC or COMP. Then the four-digit course number. Then the credit value as a decimal. Finally, the grade with modifiers like A-plus or B-minus. The last optional capture group handles status flags like CUR for current, RP for repeated, and so on.

This pattern matches exactly how Carleton formats course entries in the audit, allowing us to extract all relevant fields in one pass through the document."


[SLIDE 7: PROCESSING MATCHES]

"To process the text, we use JavaScript's `matchAll` method with global and multiline flags. This finds all matches throughout the document and gives us access to each captured group.

For each match, we extract the individual fields. Note that we normalize the course ID by removing the space - so 'SYSC 3303' becomes 'SYSC3303'. This is important because our database stores course IDs without spaces, so normalization ensures we can look up course information later.

The `matchAll` approach is efficient because it processes the entire audit in a single pass, giving us all courses with their associated data."


[SLIDE 8: GRADE CLASSIFICATION]

"Once we have the course data, we need to classify it correctly. We check if a course is marked as 'CUR' or has a status indicating it's currently in progress.

Current and deferred courses go into the `currentCourses` array with their term information. Completed courses with passing grades go into `completedCourses` with their grade. We filter out failures - F, X, UNS, and NR grades don't satisfy prerequisites.

The key insight is that both current and completed courses can satisfy prerequisite requirements for taking future courses, but they're treated differently when grade requirements come into play, which I'll explain next."


[SLIDE 9: WHY SEPARATE CURRENT VS COMPLETED?]

"Why separate these two categories? Both current and completed courses can satisfy the basic prerequisite requirement that you've 'taken' a course. For example, if you're currently taking SYSC 3303 and want to take SYSC 4406 next term which requires it, that prerequisite is satisfied.

However, some prerequisites have minimum grade requirements, like 'C- or higher'. Completed courses have grades, so we can verify the requirement is met. Current courses don't have grades yet, so we can't verify grade requirements. In this case, current courses satisfy the 'course taken' condition but not the grade condition.

This separation allows our scheduler to give accurate feedback about which requirements are satisfied and which are still pending."


[SLIDE 10: HANDLING REPEATED COURSES]

"Students sometimes retake courses, so we need to handle duplicates. We use two sets to track what we've seen - one for completed courses and one for current courses.

Before adding a course, we check if it's already in the set. If it is, we skip it. This means if a student failed a course and is retaking it, we only record the current attempt. Or if they're retaking to improve a grade, we only keep the current or most recent attempt.

For example, if the audit shows SYSC 2004 with an F in one term and a B-plus in another, we filter out the failed attempt and only keep the passing grade. This ensures our data reflects the student's actual academic standing."


[SLIDE 11: STUDENT INFO EXTRACTION]

"Beyond courses, we also extract student information using simpler regex patterns. The student ID is the first nine-digit number in the document. The name is extracted in 'Lastname, Firstname' format and reordered to 'Firstname Lastname'. And the program is extracted from text following 'Bachelor of Engineering'.

These patterns are more forgiving than the course pattern because student info appears less consistently in audits. But they're sufficient for our purposes - we need the student ID and program for validation, and the name is displayed in the UI for confirmation."


[SLIDE 12: HOW PARSED DATA IS USED]

"So how is all this parsed data used? There are two main applications.

First, prerequisite validation. When a user selects a course to add to their schedule, we check whether the required courses are in their completed or current course lists, and whether any grade requirements are met. This happens in real-time as users build their schedule.

Second, schedule generation. Users upload their audit, select courses they're interested in, and our system uses the parsed data to filter out courses they've already completed, validate prerequisites for their selections, and generate conflict-free schedules. All of this happens in one session without requiring user accounts."


[SLIDE 13: AUDIT PARSING SUMMARY]

"To summarize the audit parsing section: our technical approach uses `pdftotext -layout` for deterministic text extraction, regex patterns for fast parsing, and careful grade classification to handle various academic statuses.

Our key design decisions: choosing `pdftotext` over OCR for accuracy, using the `-layout` flag to preserve row structure, using regex for its simplicity and speed, separating current from completed courses for proper grade validation, using sets to handle course repeats, and filtering out failed grades since they don't satisfy prerequisites.


[SLIDE 14: COURSE SEARCH: THE PROBLEM]

"Now let's move to the second part of my presentation: search optimization. When users search for courses, they type in a search box and expect real-time results.

The problem is that a naive implementation makes an API call and database query for every keystroke. If a user types 'SYSC4001', that's eight keystrokes, meaning eight separate database queries. This creates unnecessary server load, especially with concurrent users, and provides a poor user experience as results flicker with each response."


[SLIDE 15: THREE OPTIMIZATION STRATEGIES]

"We implemented three strategies to solve this. First, a minimum length threshold - we don't search for queries under two characters. Single letters match too many courses and aren't useful anyway.

Second, debouncing - we wait 300 milliseconds after the user stops typing before making an API call. This means we only execute one search for a rapidly typed query, not one per keystroke.

Third, caching - we store search results in memory for five minutes. If a user searches for the same course again, or another user searches the same term during a session, we return cached results without hitting the database.


[SLIDE 16: DEBOUNCING IMPLEMENTATION]

"Here's how debouncing works. We use a reference to store a timer ID. Each time the user types, we clear any existing timer and start a new one. The search only executes after the timer expires, meaning the user has stopped typing for 300 milliseconds.

This is implemented with a `useRef` to persist the timer across renders. The effect is that typing 'SYSC4001' quickly results in exactly one API call, not eight. The user sees stable results and the server receives one well-formed query instead of multiple partial ones."


[SLIDE 17: CACHING IMPLEMENTMENT]

"For caching, we use an in-memory Map that stores query results with timestamps. When a search is requested, we first check if we have a cached result for that query. If the cache is less than five minutes old, we return it immediately without any API call. Only on a cache miss do we fetch from the database and store the result.

The cache lives in browser memory, not localStorage, so it's cleared when the tab closes. A five-minute TTL covers typical usage patterns without risking stale data - course data doesn't change during a user session, and five minutes is long enough to benefit from repeated searches but short enough that data doesn't become outdated."


[SLIDE 18: BACKEND SEARCH ENDPOINT]

"On the backend, our search endpoint is straightforward but efficient. It accepts a query and an optional limit parameter. We search both course IDs and titles case-insensitively, so users can search by code like 'SYSC3303' or by title keywords.

We filter to only show courses that have available sections - there's no point showing a course that can't be scheduled. Results are limited to 20 by default with a maximum of 100 to prevent overwhelming the UI or the database.


[SLIDE 19: OPTIMIZATION RESULTS]

"These optimizations have a significant impact. Let's look at some scenarios. Typing 'SYSC4001' went from 8 requests down to 1. Searching for 'SYSC' twice went from 2 requests to 1 thanks to caching. Typing a single character 'S' and deleting it went from 1 request to 0 because of the minimum length threshold. And a complex typing pattern with pauses went from many requests down to just 2.

In a typical session with 50 or more keystrokes, we only need about 5 to 10 actual searches. Combined, these strategies dramatically reduce API calls and server load while improving user experience.

To summarize: minimum length filtering eliminates useless queries, debouncing consolidates typing into single searches, and caching avoids repeated queries for the same terms.

Our search optimizations significantly reduce server load while improving user experience through debouncing and caching. Together, these components enable the Carleton Smart Course Scheduler to function efficiently without requiring user accounts or persistent sessions.
