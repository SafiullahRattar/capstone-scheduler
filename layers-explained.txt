UNDERSTANDING THE LAYERS
========================

Imagine building a house. You don't do everything at once - you pour the 
foundation first, then build walls, then add the roof. Each part has a 
specific job and they stack on top of each other.

Software works the same way. We organize code into "layers" where each 
layer has ONE job and talks to the layers next to it.


THE THREE LAYERS IN OUR PROJECT
===============================

    +--------------------------------------------------+
    |              APPLICATION LAYER                    |
    |          (server/ and src/ folders)              |
    |                                                  |
    |   What users see and interact with:              |
    |   - React UI (buttons, forms, schedule view)     |
    |   - API routes (URLs the frontend calls)         |
    |                                                  |
    |   This layer ONLY talks to the database.         |
    |   It doesn't know anything about HTML files      |
    |   or how data was originally fetched.            |
    +--------------------------------------------------+
                          |
                          | (queries the database)
                          v
    +--------------------------------------------------+
    |              DATABASE LAYER                       |
    |             (prisma/ folder)                     |
    |                                                  |
    |   Where all the data lives permanently:          |
    |   - Course table (SYSC3303, COMP1405, etc.)      |
    |   - Section table (times, days, CRNs)            |
    |   - PrerequisiteNode table (the tree structure)  |
    |                                                  |
    |   Prisma is the "translator" - it takes          |
    |   JavaScript code and turns it into SQL          |
    |   commands that PostgreSQL understands.          |
    +--------------------------------------------------+
                          ^
                          | (seeds/populates the database)
                          |
    +--------------------------------------------------+
    |               DATA LAYER                          |
    |            (scripts/ folder)                     |
    |                                                  |
    |   Gets data from the outside world:              |
    |   - curl fetches from Carleton's servers         |
    |   - Parsers read HTML and TSV files              |
    |   - Outputs JSON files                           |
    |   - seed.ts loads JSON into the database         |
    |                                                  |
    |   This layer talks to Carleton's websites        |
    |   and produces clean data for the database.      |
    +--------------------------------------------------+


WHY SEPARATE INTO LAYERS?
=========================

1. EASIER TO FIX PROBLEMS

   If Carleton changes their website, you only need to fix the Data Layer.
   The Application Layer and Database Layer don't need any changes.
   
   Example: If the timetable format changes from tabs to commas:
   - Fix: Edit import-timetable.ts (Data Layer)
   - Don't touch: React UI, API routes, database schema


2. EASIER TO UNDERSTAND

   Each layer has ONE job:
   - Data Layer: "Get data from Carleton"
   - Database Layer: "Store and organize data"
   - Application Layer: "Show data to users"
   
   When something breaks, you know where to look.


3. EASIER TO TEST

   You can test each layer separately:
   - Test the parser with a sample HTML file
   - Test the database with fake data
   - Test the UI without needing real course data


4. EASIER TO REPLACE PARTS

   Want to switch from PostgreSQL to MySQL?
   - Change: Database Layer (Prisma config)
   - Don't touch: Data Layer or Application Layer
   
   Want to switch from React to Vue?
   - Change: Application Layer (src/ folder)
   - Don't touch: Data Layer or Database Layer


HOW DATA FLOWS THROUGH THE LAYERS
=================================

Step 1: DATA LAYER fetches from Carleton
        
        curl --> sectiondata.txt (raw timetable)
        curl --> courses/*.html (course pages)


Step 2: DATA LAYER parses into JSON
        
        sectiondata.txt --> import-timetable.ts --> (directly to DB)
        courses/*.html --> Python parser --> course_prerequisites_simple.json


Step 3: DATA LAYER seeds the DATABASE LAYER
        
        course_prerequisites_simple.json --> seed.ts --> PostgreSQL tables


Step 4: APPLICATION LAYER reads from DATABASE LAYER
        
        React UI --> API route --> Prisma query --> PostgreSQL
        
        Example: User clicks "Show SYSC3303 prerequisites"
        1. React sends request to /api/courses/SYSC3303/prerequisites
        2. API route calls prisma.prerequisiteNode.findMany()
        3. Prisma translates to SQL: SELECT * FROM prerequisite_nodes WHERE...
        4. PostgreSQL returns the data
        5. API sends JSON back to React
        6. React displays it on screen


THE SCRIPTS IN THE DATA LAYER
=============================

Each script does ONE thing (this is called "high cohesion"):

+---------------------------+-----------------------------------+------------------+
| Script                    | What It Does                      | Output           |
+---------------------------+-----------------------------------+------------------+
| curl (command line)       | Downloads raw data from Carleton  | .txt, .html files|
+---------------------------+-----------------------------------+------------------+
| fetch-all-course-titles.ts| Downloads course HTML pages       | courses/*.html   |
+---------------------------+-----------------------------------+------------------+
| parse_prerequisites.py    | Reads HTML, extracts prereqs      | JSON file        |
+---------------------------+-----------------------------------+------------------+
| merge-course-data.ts      | Combines titles + prerequisites   | Combined JSON    |
+---------------------------+-----------------------------------+------------------+
| import-timetable.ts       | Parses timetable, inserts to DB   | Section table    |
+---------------------------+-----------------------------------+------------------+
| seed.ts                   | Reads JSON, builds tree in DB     | Course + Node    |
|                           |                                   | tables           |
+---------------------------+-----------------------------------+------------------+

Why so many scripts instead of one big one?

If you had ONE script that did everything:
- Hard to debug (where did it break?)
- Hard to re-run (have to redo everything)
- Hard to modify (changing one thing might break another)

With separate scripts:
- Easy to debug (run just the broken one)
- Easy to re-run (only re-run what you need)
- Easy to modify (each script is independent)


REAL EXAMPLE: WHAT HAPPENS WHEN A USER LOADS THE APP
====================================================

1. User opens the scheduler in their browser

2. APPLICATION LAYER (React) loads and asks:
   "What courses are available for Winter 2025?"

3. APPLICATION LAYER (API route) receives the request:
   
   // server/routes/courses.ts
   app.get('/api/courses', async (req, res) => {
     const courses = await prisma.course.findMany()
     res.json(courses)
   })

4. DATABASE LAYER (Prisma) translates to SQL:
   
   SELECT * FROM courses;

5. PostgreSQL returns all courses

6. APPLICATION LAYER (React) displays them in a list

Notice: The React code has NO IDEA that data originally came from:
- A curl command
- HTML files
- A Python parser
- JSON files

It just asks the database and gets clean data back. That's the power of layers.


ANALOGY: A RESTAURANT
=====================

Think of it like a restaurant:

DATA LAYER = The suppliers and kitchen prep
- Suppliers deliver raw ingredients (curl fetches data)
- Prep cooks clean and chop vegetables (parsers clean data)
- Everything gets organized in the pantry (JSON files)

DATABASE LAYER = The pantry and refrigerator  
- Organized storage for all ingredients
- Chefs grab what they need without knowing where it came from
- Everything is labeled and easy to find

APPLICATION LAYER = The dining room and waiters
- Customers (users) see the menu and order food
- Waiters (API) take orders to the kitchen
- Food (data) comes back beautifully presented

The customer doesn't need to know:
- Which farm the vegetables came from
- How the prep cook chopped them
- Which shelf they were stored on

They just order "Caesar Salad" and get a salad.

Same with our app - users click "Show prerequisites" and see prerequisites.
They don't know about curl, HTML parsing, or tree structures.


SUMMARY
=======

Layer              | Folder(s)      | Job                    | Talks To
-------------------|----------------|------------------------|------------------
Data Layer         | scripts/       | Fetch & parse data     | External websites
                   |                |                        | --> Database
-------------------|----------------|------------------------|------------------
Database Layer     | prisma/        | Store & organize data  | Data Layer
                   |                |                        | <--> App Layer
-------------------|----------------|------------------------|------------------
Application Layer  | server/, src/  | Show data to users     | Database only

Key benefits:
- Each layer has ONE job
- Layers are independent (can change one without breaking others)
- Easy to debug, test, and maintain
