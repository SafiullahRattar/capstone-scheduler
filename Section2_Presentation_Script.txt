# Section 2 Presentation Script: Prerequisite Representation
## 10-Minute Presentation in Layman Terms

## SLIDE 2 (2.1 Original): Opening - 1 minute

"Good morning. Today I'm going to explain how our system handles prerequisites, these are rules that say you have to take certain courses before you can take others.

Here's was the challenge: these rules use everyday language that humans understand, but computers don't. Taking SYSC 4805 requires Fourth-year Standing OR permission. Taking SYSC 4001 requires SYSC 3303 AND (SYSC 3310 OR SYSC 3320). The hard part is translating these sentences into something a computer can actually check.

## SLIDE 3
First we had to figure out how to Store these rules in a database,so that we can evaluate it against a student's audit to figure out what courses they've taken, which will allow us to tell the student clearly what's missing, or start generating schedules.

## Slide 4
"What did we need to build? Three things:

First, store these rules in a database—not just as text, but as structured data that the computer can actually use.

Second, handle different types of requirements. Prerequisites aren't all the same. Some are courses you need to take. Some check what year you're in. Some require special permission from a professor. Some need a minimum grade, like C- or higher.

Third, handle nested logic. This is the tricky part. Some prerequisite rules have AND inside OR inside AND. For example, 'SYSC 4001 requires SYSC 3303 AND (MATH 1001 OR (MATH 1140 AND SYSC 3303))'. The system needs to understand and evaluate these complex nested rules."

## SLIDE 5: What Are Prerequisites? (NEW) - 1 minute

"Let me start with a simple example of what a prerequisite is.

Think of it like building a house. You can't put the roof on before you have walls, and you can't have walls before you have a foundation. Each step depends on the previous step being done first.

In university courses, it's the same idea. Some courses build on top of others. You can't take an advanced course without first taking the foundational course that teaches you what you need to know.

Some prerequisites are simple: you just need one course. But some are more complex like this one. So how do we evaluate these rules? What Structure do we use?
---

## SLIDE 6: The Tree Structure (NEW) - 1.5 minutes

"We draw them as something called a tree.

Imagine a family tree. At the top, you have a grandparent. They have children, and those children might have their own children.

For our prerequisite rule, the top box represents the main requirement. It says "AND"—this means everything under it must be satisfied.

Looking at the left side, we have a course: SYSC 3303. That's straightforward—you just need that course.
:
On the right side, we have an "OR" group. This means you only need ONE of the courses listed inside it—either SYSC 3310 OR SYSC 3320. You don't need both.

So the whole rule reads as: You need SYSC 3303 AND at least one of those two courses. The tree makes this easy to see and understand."

---

## SLIDE 7 (2.2 Original): Database Schema - 1.5 minutes

"So how do we store this in a computer database?

We created something called a "self-referential table." That sounds complicated, but it just means each row in the table can point to another row in the same table—like a family tree where each person knows who their parent is.

Each row represents one piece of our requirement. There are five types of pieces:

- **AND** – everything under it must be satisfied
- **OR** – you only need one option from under it
- **COURSE** – a specific course like SYSC 3303
- **YEAR_STANDING** – checking if you're in the right year
- **PERMISSION** – needing approval from a professor

Each row knows which row is above it in the tree. This lets us build trees of any size and complexity, all in one simple table."

---

## SLIDE 8: How We Store the Tree (NEW) - 1 minute

"Let me show you what this actually looks like in the database.

Each row has: an ID, what type of node it is, what course it refers to, and who its parent is.

Look at the first row—it's the root, the top of the tree. It has no parent because it's at the top.

The second row is a course node, and its parent is the first row. That means it's a child of the AND node.

The third row is an OR node, and its parent is also the first row.

The fourth and fifth rows are courses, and their parent is the third row—the OR node.

If you follow the parent IDs, you can reconstruct the entire tree. It's a simple but powerful way to store complex rules."

## SLIDE 9 (2.3 Original): Expression Parser - 1 minute

"Now, the JSON File give us these requirements as plain English text—like 'SYSC3303 AND (SYSC3310 OR SYSC3320)'. We needed to turn this text into the tree structure I just described.

We first identify the main AND at the top level. Then we see there's an OR group inside the parentheses. Then we handle the parentheses for nesting. Finally, we identify the individual courses.

Each piece becomes a node in our tree, and the relationships between them are preserved."

---

## SLIDE 10 (2.4 Original): Term Recognition - 0.5 minutes

"Once we've broken the expression into individual terms, we figure out what type of term each one is.

Is it a course code like SYSC 3303? Is it a grade requirement like 'C- or higher'? Is it a year standing like 'fourth year'? Or is it permission from a professor?

Each term becomes a simple node with a type that our system can understand and evaluate later."

---

## SLIDE 11 (2.5 Original): Tree Storage - 0.5 minutes

"After parsing, we save this tree to the database. We do this recursively—we start at the top and work our way down, creating each node and linking it to its parent.

For our example: we first create the AND node (the root, with no parent). Then we create the SYSC 3303 course node and link it to the AND node. Then we create the OR node and link it to the AND node. Finally, we create the two course nodes and link them to the OR node.

Each row knows who its parent is, so we can walk up and down the tree when we need to check if a student meets the requirements."

---

## SLIDE 12 (2.6 Original): Evaluation Algorithm - 0.5 minutes

"This is where everything comes together. To check if a student can take a course, we evaluate their transcript against the prerequisite tree.

We walk through the tree:
- For an AND node, we check ALL of its children. If any child fails, the whole AND fails.
- For an OR node, we check its children one by one. As soon as ONE child passes, the OR passes.
- For a COURSE node, we look at the student's completed courses.

The key advantage of the tree structure is that we can give detailed feedback about exactly which courses are missing."

---


## SLIDE 13 (2.7 Original): Grade Checking - 0.5 minutes

"Some courses don't just require that you've taken a prerequisite—they require that you've done well enough. For example, some courses need a C-minus or higher in the prerequisite.

To handle this, we assigned each letter grade a number: A+ is 12, A is 11, A- is 10, and so on down to F at 0. When checking a grade requirement, we just compare the numbers. If you have a B and need a C-, you pass. If you have a D and need a C-, you don't.

This makes it easy to check grade requirements automatically."

---

## SLIDE 14 (2.8 Original): User Feedback - 0.5 minutes

"Finally, we package all of this into a clear result for the student. We tell them:
- Is the prerequisite satisfied or not?
- If not, which specific courses are they missing?
- Are there any grade issues?
- Do they need special permission?

This gives students actionable information so they know exactly what to do next, rather than just seeing a 'failed' message."

SLIDE 14: RELATIONAL SCHEMA
"Our system uses a PostgreSQL database with five interconnected models. Let me walk through how they relate to each other.
The Course model is the central table. It represents all 348 courses in our catalog. Each course stores basic information like its ID, title, description, and credit value. But more importantly, the Course model has relationships to several other tables.
First, a Course can have multiple PrerequisiteNodes—the individual pieces that make up a prerequisite tree. We'll discuss those in a moment.

Second, a Course can have a Prerequisite record, which stores the human-readable prerequisite expression as text. For example, 'SYSC3303 && (SYSC3310 || SYSC3320)'. This is a one-to-one relationship—one course has one prerequisite expression.

Third, a Course can have multiple Sections—these are the actual timetabled offerings like Lecture A, Lab B1, or Tutorial C. There are over 7,600 sections in our database.

Fourth, a Course can be referenced by PrerequisiteNodes that require it. When a prerequisite says 'SYSC3303', a node links back to the Course table to verify that course exists.
The Prerequisite model is simple. It has a one-to-one relationship with Course, using courseId as both its primary key and foreign key. It stores the raw prerequisite expression string.

The PrerequisiteNode model is the most complex—it's a self-referential tree structure. Each node has:
- A courseId linking back to the Course this prerequisite belongs to
- A parentId pointing to another node in the same table (or null for root nodes)
- A children array containing all nodes that point to it as their parent
- An optional requiredCourseId linking to a Course that this node requires
This self-reference through parentId is what allows us to build trees of arbitrary depth and complexity.
The Student model represents individual students. It stores their student ID number, name, and program. Each Student can have multiple CourseCompletions.

The CourseCompletion model is a join table that links Students to Courses they've completed. It has:
- A studentId linking to Student
- A courseId linking to Course
- A grade field for the grade received
- A composite unique constraint on [studentId, courseId]—a student can't complete the same course twice

The Section model represents individual class sections. Each section belongs to one Course via courseId. Sections contain scheduling information like days, times, location, instructor, and capacity.
